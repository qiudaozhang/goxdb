# 基准：goxdb vs sqlx vs GORM vs bun

四个框架跑在**同一进程、同一个 `*sql.DB` 连接池、同一张表**上，只做一次迭代分组，
因此数值差异来自框架本身，而不是连接数、预热或网络抖动。

两套基准，回答两个不同的问题：

| 目录 | 目的 | 数据源 |
|---|---|---|
| `../bench_test.go`（仓库根） | 框架**纯开销**：元数据查找、SQL 渲染、反射扫描 | 内存假驱动，不联网 |
| `./`（本目录） | **端到端**：框架 + 驱动 + 服务端，含真实往返 | 真实 MySQL / PostgreSQL |

## 环境

- macOS darwin/arm64，Apple M4，Go 1.27.1
- MySQL 8.4（`docker compose up -d --wait`）
- PostgreSQL 17（同上）
- sqlx v1.4.0 / GORM v1.31.2 / bun v1.3.0
- 连接池 32（`MaxOpen` = `MaxIdle`），`-benchtime 1s -count 3`，表中为**中位数**

## xdb 相对最优实现的比例

| 场景 | PostgreSQL | MySQL |
|---|---:|---:|
| 分页 / 批量插入 / 纯渲染 | **1.00x** | 1.00x |
| 事务 / 条件计数 | 1.00–1.02x | 1.58x |
| 单行读 / 批量读 / 插入 / 预加载 | 1.04–1.05x | 1.07–1.88x |
| 更新 / Upsert / 并发 | 1.04–1.09x | 1.58–2.04x |
| JOIN 聚合 | 1.00x² | 1.25x³ |

PostgreSQL 上 xdb 与最优实现相差普遍在 5% 以内；MySQL 上的差距几乎全部来自
bun 的参数插值（见下文第 2 点），不是框架开销。

² 原表为 1.16x，是统计信息过期造成的假象，见第 6 点；修正后与 sqlx / bun 同档（上表其余数字未重跑）。
³ 与 MySQL 其它场景一样来自 bun 的参数插值：开 `interpolateParams=true` 并逐个框架单独运行时，
xdb 451–480 μs、bun 449–461 μs，在噪声范围内。

## 零反射扫描器的收益

`xdb+gen` 与 `xdb` 使用完全相同的构建器、SQL 与连接池，唯一区别是结果类型由
`goxdb gen` 生成过 `NewRowScanner`。同一进程内交替测量：

| 数据库 | 场景 | 反射扫描 | 生成代码 | 提升 |
|---|---|---:|---:|---:|
| postgres | 读 1 行 | 118.6 μs | 113.3 μs | 4.5% |
| postgres | 读 100 行 | 202.1 μs | 197.6 μs | 2.2% |
| mysql | 读 1 行 | 210.8 μs | 213.4 μs | -1.3% |
| mysql | 读 100 行 | 295.3 μs | 281.3 μs | 4.7% |

隔离测量（假驱动，无网络）时收益更清楚：90 行扫描 `19.2 μs → 15.6 μs`，**-19%**，
即每行省约 40 ns。真实数据库上这部分被往返噪声部分掩盖，单行读在 MySQL 上
甚至落到噪声里。**结论：批量读有稳定收益，单行读收益在测量误差内。**

## 怎么读这些数字

**1. 真实往返主导一切，框架之间差距普遍在 5% 以内。**
单行查询 PG 约 113 μs、MySQL 约 228 μs，而框架自身的 SQL 生成只有 0.6–1.2 μs。
想靠换 ORM 提升吞吐，收益上限就在个位数百分比；真正的杠杆是往返次数、
索引与查询计划。

**2. MySQL 上 bun 快 1.5–2 倍，是驱动差异，不是框架差异。**
`go-sql-driver/mysql` 默认对带参语句先 `PREPARE` 再 `EXECUTE`（两次往返）；
bun 默认把参数插值进 SQL 文本（一次往返）。给 DSN 加 `interpolateParams=true` 后：

```
BenchmarkSelectOne/mysql   xdb 108μs  sqlx 104μs  gorm 117μs  bun 118μs
BenchmarkUpdateOne/mysql   xdb  98μs  sqlx  94μs  gorm 100μs  bun  96μs
```

差距消失，四者持平。**生产环境开 `interpolateParams=true` 前注意**：它把参数拼进
SQL 文本，历史上有过字符集相关绕过；确认驱动版本 ≥ 1.8 且库/表字符集一致再用。
goxdb 默认不替用户做这个决定。

**3. PostgreSQL 上 bun 插入慢 2 倍，是它的 `RETURNING *` 设计。**
bun 在 PG 下为每条 INSERT 生成 `RETURNING` 并回扫整行（为了填充默认值字段），
xdb 只 `RETURNING id`。批量插入同理：bun `1963 μs` vs xdb `913 μs`。
这不是 bug，是 bun 用额外往返换取「插入后模型字段完全可用」的语义。

**4. GORM 的分配最高，主要来自每次查询构建 `*gorm.Statement` 与闭包链。**
读 1 行约 5 KB / 69 次分配。往返成本掩盖了它，时间上看不出差别；
在高 QPS + 小结果集的场景下 GC 压力会更明显。

**5. 框架自身的分配热点已修复。**
此前 `Query[T]` 每次构造都重建 15 个 `colNode`，`scan.NewPlan` 每次都重建
「列名 → 字段」映射。现在列清单按模型缓存、扫描计划按 `(类型, 列集合)` 缓存，
构建器也不再为每个标识符/占位符生成临时字符串：

| 基准（fake 驱动） | 优化前 | 优化后 |
|---|---:|---:|
| `Query[T]` 构造 | 367 ns / 13 allocs | 90 ns / **2 allocs** |
| 纯 SQL 生成（含 WHERE/ORDER/LIMIT） | 1238 ns / 31 allocs | **516 ns / 15 allocs** |
| 90 行扫描 | 15157 ns / 300 allocs | 14670 ns / **211 allocs** |

纯渲染现在与 bun 同档（0.60 vs 0.60 μs），比 GORM 快一倍，且分配更少。

**6. JOIN 聚合原以为是短板（PG 1.16x、MySQL 1.25x），实为统计信息过期造成的假象。**
灌数与每个场景的清理都会让表统计过期。MySQL 曾把这条 JOIN 估成「30 个用户、1 个订单」
（实际 1000 / 5000），选出慢约 3 倍的计划；后台何时自动刷新统计是随机的，于是
谁恰好跑在刷新之后谁就快（bun 0.45 ms 对其余 1.4 ms，GORM 三次中有一次 0.6 ms）。
单独执行 bun 生成的 SQL 也是 1.28 ms，与 xdb 一致——差距不在框架。
现在 `analyzeTables` 在灌数后与每个场景清理后显式 `ANALYZE`。修正后 PG 上
xdb 254–273 μs、sqlx 262–265 μs、bun 284–291 μs，三者同档。

**7. 预加载的分配数偏高（2738 次），但时间只差 5%。**
xdb 用反射回填关联切片，sqlx 是手写两段查询 + 结构体切片赋值。
时间接近说明瓶颈在两次往返，不在回填。

## 口径与公平性

已做的对齐：

- **GORM 关闭隐式事务**（`SkipDefaultTransaction: true`）。
  默认配置下每次 `Create` / `Update` 都会包一层 `BEGIN … COMMIT`，
  多出两个往返，没有可比性。sqlx / bun / xdb 都不隐式开事务。
- **sqlx 手工补齐主键回填**：PG 用 `RETURNING id`，MySQL 用 `LastInsertId`。
  sqlx 本身不提供回填，不补的话它少做一步工作。
- **bun 的 `Scan` 与 `xdb.Query(...).All()` 语义对齐**：都读 100 行并校验行数。
- **每个场景结束都清理**：`cleanup` 删除基准写入的行并把自增序列推回种子之后，
  子基准之间互不污染（否则唯一索引与行数断言会互相干扰）。
- **每次灌数与清理后都 `ANALYZE`**：统计过期会让优化器随机选出慢计划（见第 6 点），
  结果取决于运行顺序而不是框架。
- **所有框架的模型使用同一结构体**，各自打各自的 tag（`xdb` / `db` / `bun` / `gorm`）。
- `TestCorrectness` 在跑基准前先验证**五套实现**（含 `xdb+gen`）行为一致：
  事务确实提交、自增确实回填、批量插入确实写入 100 行、Upsert 确实更新而非多插一行。
  任何框架跑错或「少干活」，基准数字就没有可比性。

已知的口径差异（无法完全消除，读表时请记住）：

- bun 在 MySQL 上做了参数插值（第 2 点），在 PG 上用了 `RETURNING *`（第 3 点）。
  两者都是 bun 的默认行为，未做特殊绕过——它们是 bun 设计的一部分，
  如实记录比强行对齐更有参考价值。
- GORM 在 `RowAffected == 0` 时的额外检查、bun 的 `BaseModel` 内嵌字段解析，
  都属于各框架的固定成本，未做特殊绕过。
- 单机 Docker + 回环网络，延迟绝对值（μs 级）不代表生产环境；
  **关注同列之间的相对关系，不要跨机比较绝对值。**

## 复现

```bash
# 1. 起数据库（仓库根目录）
docker compose up -d --wait

# 2. 跑对比基准
cd benchmark
go test -run XXX -bench . -benchtime 1s -count 3 ./...

# 3. 只跑某一项
go test -run XXX -bench 'SelectMany' -benchtime 1s -count 5 ./...

# 4. 先验证语义正确性
go test -run TestCorrectness -v ./...

# 5. 框架纯开销（不联网，内存假驱动）
cd .. && go test -run XXX -bench . -benchtime 1s ./...
```

连接串可覆盖（用于旧版本兼容性验证，配合 `docker compose --profile legacy`）：

```bash
XDB_BENCH_MYSQL_DSN='root:xdb@tcp(127.0.0.1:23306)/xdb?parseTime=true' \
XDB_BENCH_PG_DSN='postgres://postgres:xdb@127.0.0.1:25432/xdb?sslmode=disable' \
  go test -run XXX -bench . -benchtime 1s -count 3 ./...
```

数据库不可达时基准会 `Skip` 而不是失败，方便 CI 里无条件跑全量测试。
